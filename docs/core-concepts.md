# Core Concepts

PuzzleKit separates the infrastructure required to run a puzzle from the mechanics that make each puzzle unique.

This allows different puzzle types to share the same runtime while maintaining independent rules, state structures, and player interactions.

This guide explains the main concepts behind the architecture.

## 1. Puzzle Modules

A puzzle module defines the mechanics of a particular puzzle type.

It determines:

- How a puzzle is initialized.
- Which player actions are supported.
- How actions affect the puzzle state.
- When the puzzle is considered complete.
- How its state is serialized and restored.

Every module implements the `PuzzleModule` interface.

```ts
interface PuzzleModule<TConfig, TState, TActionPayload> {
  id: string;
  version: string;

  initialize(config: TConfig): TState;

  processAction(
    state: TState,
    action: PuzzleAction<TActionPayload>,
    config: TConfig
  ): ActionResult<TState>;

  isComplete(state: TState, config: TConfig): boolean;

  serialize(state: TState): string;

  deserialize(data: string): TState;
}
```

The module owns the puzzle rules. The core runtime does not need to understand how a Nonogram, Sliding Puzzle, or Lights Out game works.

## 2. Puzzle Definitions

A puzzle definition describes a particular puzzle instance before it is created.

It contains:

- `id`: A unique identifier for the definition.
- `type`: The module type required to run the puzzle.
- `version`: The definition version.
- `config`: Configuration passed to the module during initialization and other lifecycle operations.
- `constraints`: Optional validation constraints.

Example:

```ts
const definition = {
  id: "my-sliding-puzzle",
  type: "sliding-puzzle",
  version: "1.0.0",
  config: {
    size: 3,
  },
};
```

Definitions describe how a puzzle should be configured. They are separate from the state that changes as the player interacts with the game.

## 3. Puzzle State

Puzzle state represents the current condition of a puzzle instance.

Its structure is determined by the module.

For example, a Sliding Puzzle might maintain:

```ts
interface SlidingPuzzleState {
  size: number;
  tiles: number[];
  emptyIndex: number;
  moves: number;
}
```

A Lights Out puzzle instead maintains a collection of light states and a move counter.

The runtime manages state storage, while the module determines how that state changes.

## 4. Actions

Actions represent player intentions rather than direct state modifications.

For example, a player selecting a tile in a Sliding Puzzle might produce:

```ts
const action = {
  type: "MOVE_TILE",
  payload: {
    tileIndex: 4,
  },
};
```

The runtime dispatches the action to the appropriate module.

The module determines whether the action is valid and returns either an accepted result with a new state or a rejected result.

This keeps game rules out of the user interface.

## 5. Action Results and Feedback

Modules return an `ActionResult` when processing an action.

An accepted result can contain:

- The updated state.
- Feedback messages.
- Events generated by the module.

A rejected result contains a reason and may also contain feedback or events.

Feedback communicates information to the player, such as an invalid move or a helpful hint.

This allows applications to decide how feedback should be presented without coupling presentation logic to the engine.

## 6. Constraints

Constraints provide reusable validation logic that can be applied to puzzle definitions, actions, or state.

For example, a uniqueness constraint can ensure that a collection contains no duplicate values.

PuzzleKit supports built-in constraints and custom registered constraints.

Constraints complement module-specific rules. They do not replace the mechanics implemented by puzzle modules.

See the [Constraints Guide](./constraints.md) for details.

## 7. Puzzle Runtime

The runtime coordinates the different components required to manage puzzle instances.

It handles:

- Module registration.
- Puzzle creation and restoration.
- Instance management.
- State management.
- Action dispatching.
- Constraint validation.
- Completion checking.
- Event management.
- Session serialization.

Developers interact with the runtime instead of managing these components individually.

Example:

```ts
const runtime = new PuzzleRuntime();

runtime.registerModule(slidingPuzzleModule);

const puzzle = runtime.create({ definition });
```

## 8. Puzzle Handle

Creating a puzzle returns a `PuzzleHandle`.

The handle provides the public interface for interacting with that particular puzzle instance.

Common operations include:

```ts
const state = puzzle.getState();

puzzle.dispatch({
  type: "MOVE_TILE",
  payload: { tileIndex: 4 },
});

const completed = puzzle.isComplete();

const savedSession = puzzle.serialize();

puzzle.reset();

puzzle.destroy();
```

The handle provides access to puzzle operations without exposing the internal runtime components.

## 9. Events

Events communicate significant occurrences during a puzzle's lifecycle.

Examples include:

- `puzzle:initialized`
- `action:accepted`
- `action:rejected`
- `state:updated`
- `puzzle:completed`
- `puzzle:reset`

Applications can subscribe to events to respond to changes without embedding additional logic inside puzzle modules.

For example, an application could listen for `puzzle:completed` to display a completion screen.

## 10. Serialization and Restoration

PuzzleKit supports saving and restoring puzzle sessions.

A serialized session contains the puzzle definition, instance metadata, module version, and serialized state.

The module is responsible for serializing and deserializing its own state.

This allows an application to preserve a player's progress and restore the puzzle later.

## 11. Framework Independence

The core engine does not depend on a particular UI framework.

Developers can build interfaces using their preferred frontend technology and connect them to the runtime.

PuzzleKit also provides a React adapter containing:

- `PuzzleProvider`
- `usePuzzle`
- `usePuzzleState`

These provide a convenient way to access puzzle instances and subscribe to state updates in React applications.

See the [React Integration Guide](./react-integration.md).

## Putting It Together

The typical lifecycle of a puzzle looks like this:

```text
Puzzle Definition
       |
       v
Puzzle Runtime
       |
       v
Module Initialization
       |
       v
Puzzle Instance
       |
       v
Player Action
       |
       v
Action Dispatcher
       |
       v
Constraint Validation
       |
       v
Module Processes Action
       |
       v
State Updated
       |
       v
Completion Checked
       |
       v
Events Emitted
```

The central idea behind PuzzleKit is that the runtime provides reusable infrastructure, while puzzle modules provide the mechanics.
